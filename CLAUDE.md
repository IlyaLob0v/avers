# CLAUDE.md — правила проекта «Аверс»

Этот файл читает каждая сессия Claude Code в репозитории. Здесь только то, что нужно знать всегда.
Подробности — в `docs/`.

## Что это за проект

Замена старой системы учёта антенной службы (Омск) на новую.

- **Было:** 8+ отдельных программ на Delphi 6 + BDE, Java-модули (AversContracts, ImportPay, SMS),
  база Oracle 10.2 (схема `JACK`, сервер `servora`, алиас `avers102`), клиент Oracle 9 на рабочих местах.
- **Будет:** единое рабочее место (Avalonia 12, .NET 10 LTS) + сервер приложений (ASP.NET Core) +
  PostgreSQL + веб-просмотр для радиомехаников с телефона + обмен с 1С 8.3.
- **Уже есть:** оболочка интерфейса (сентябрь 2026), перенесена из `D:\Avers\Source` (исходный вид — ветка
  `import/shell-net8`) и переведена на .NET 10 / Avalonia 12 / SQLite (PR #1, см. `src/README.md`).

## Облачные сессии

`.claude/hooks/session-start.sh` (SessionStart-хук) в облаке ставит .NET 10 SDK из архива Ubuntu и делает
`dotnet restore`, поэтому сборка и тесты доступны сразу. На ПК хук ничего не делает.

## Команды

```bash
dotnet build Avers.sln            # сборка
dotnet test Avers.sln             # тесты
dotnet format Avers.sln           # форматирование
AVERS_TEST_POSTGRES="Host=localhost;Username=avers;Password=…" dotnet test tests/Avers.Server.Tests   # серверные тесты на PostgreSQL
docker compose -f db/docker-compose.yml up -d            # локальный PostgreSQL
docker compose -f db/docker-compose.yml --profile legacy up -d   # + Oracle Free для выгрузки JACK
```

В VS Code те же команды есть в задачах (`Ctrl+Shift+B` — сборка).

## Как работать с кодом

Для тривиальных задач действуй по здравому смыслу.

1. **Думай перед кодом.** Не додумывай молча: явно называй допущения. Если просьбу можно понять
   по-разному, покажи варианты, а не выбирай втихую. Если есть путь проще, скажи об этом.
   Если что-то неясно, остановись и спроси.
2. **Простота прежде всего.** Пиши минимум кода, который решает задачу. Никаких функций сверх просьбы,
   абстракций для одного места, «гибкости» и настроек, о которых не просили, обработки невозможных ошибок.
   Если 200 строк можно сделать в 50, перепиши.
3. **Точечные правки.** Трогай только то, что нужно. Не «улучшай» соседний код, комментарии и форматирование,
   не рефактори то, что работает, держись существующего стиля. Чужой мёртвый код не удаляй, а упомяни;
   убирай только то, что стало лишним из-за твоих правок. Каждая изменённая строка должна вести к просьбе пользователя.
4. **Работа на результат.** Превращай задачу в проверяемую цель: для ошибки сначала пиши тест, который её
   воспроизводит, потом исправляй; при рефакторинге тесты должны проходить до и после. Для многошаговых задач
   дай короткий план: шаг, затем как проверить.

## Жёсткие правила

1. **Боевые базы — только чтение**, и только когда пользователь разрешил в этой сессии.
2. **Персональные данные абонентов не коммитить.** Выгрузки — в `db/legacy/dumps/` (игнорируется git).
3. **Секреты не коммитить.** Пароли — в `.env` (по образцу `.env.example`) или user-secrets.
4. **Схема старой базы в PDF «существующие решения» — догадки по скриншотам.** Источник правды — DDL схемы `JACK`.
5. **Деньги — `decimal`.** Суммы сверять с бумажной сверкой бухгалтерии (август 2026: ОЭК 4 914 739,57).
6. **Права проверяет сервер**, клиент только прячет недоступные кнопки.
7. Значимое решение = ADR в `docs/adr/`.
