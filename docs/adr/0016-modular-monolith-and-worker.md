# ADR-0016. Модульный монолит и фоновая служба

- Статус: Принято 22.10.2026 в части «монолит + отдельная фоновая служба»; передача заданий через таблицу в PostgreSQL — Предложено
- Дата: 2026-11-06
- Участники: Илья, архитектор

## Контекст
Сейчас сервер — один процесс `Avers.Server` (`src/Avers.Server/Program.cs`): Minimal API, база через `AddAversDatabase`
(`Hosting/Database.cs`), при запуске — миграции EF, команда администратора `set-password` (`Hosting/AdminCommands.cs`).
Фоновых задач нет: ни `IHostedService`, ни `BackgroundService` в коде не используются. Служба systemd одна —
`deploy/server/avers-server.service`.

Долгая работа уже идёт внутри HTTP-запроса: загрузка файла ОЭК (`PaymentEndpoints.ImportOek` → `OekImport.Apply`)
читает в память всех абонентов и все месяцы и пишет их одним `SaveChanges`, без блокировки строк. Оплата ОЭК ставится
в месяц без условия «месяц ещё не оплачен» в самом `UPDATE` (в отличие от `Payments.Record`): если кассир внесёт
оплату этого месяца, пока идёт загрузка, загрузка её затрёт.

Впереди ещё три таких задачи:
- загрузка банковских реестров DBF — перенос ImportPay (35 форматов; в старой системе через буфер `ABN_PAY_BUFF`
  и процедуру `IMPORTPAYFROMBUFF`, `docs/01-current-system.md`);
- обмен с 1С по OData (ADR-0006, этап 2): сеть, тайм-ауты, повторы;
- ночные отчёты (какие именно — ещё не названо).

Касса не должна ждать, пока идёт загрузка реестра на десятки тысяч строк. Команда маленькая, сервер один
(Ubuntu в Hyper-V на сервере 1С, Q-06), база одна (ADR-0002).

## Варианты
1. **Всё в процессе `Avers.Server` через `BackgroundService` / `IHostedService`.** Плюсы: ни нового проекта, ни новой
   службы; общая настройка и DI. Минусы: импорт делит с кассой процессор, память, пул потоков и пул соединений;
   сбой импорта (нехватка памяти) роняет и кассу; обновление или перезапуск сервера обрывает идущую загрузку —
   по умолчанию на остановку даётся 30 секунд; нельзя перезапустить импорт, не выкинув сотрудников.
2. **Отдельный процесс-служба `Avers.Worker`** (шаблон Worker Service, `Microsoft.Extensions.Hosting.Systemd`),
   своя служба systemd рядом с сервером, та же база PostgreSQL, тот же `Avers.Data`. Плюсы: долгие задачи изолированы
   (свой процесс, свой пул соединений, пониженный приоритет); служба перезапускается независимо от сервера;
   правила записи те же, что у кассы. Минусы: второй проект и второй unit systemd; нужен способ передать задание
   от сервера службе; версии сервера и службы должны совпадать (одна схема базы).
3. **Микросервисы и брокер сообщений** (RabbitMQ и т. п.). Плюсы: масштабирование по частям. Минусы: брокер — ещё
   одна система, которую надо ставить, копировать и чинить; распределённые транзакции вместо одной транзакции
   в одной базе; для одного сервера и 45 000 абонентов выгоды нет, а команды на сопровождение нет.

## Решение
Вариант 2. Микросервисы не вводим, остаёмся модульным монолитом: одна база, один `Avers.Data`, два процесса.

**Что делает служба.** Загрузка банковских реестров и файла ОЭК, обмен с 1С, ночные отчёты. HTTP-порта у неё нет;
сотрудники с ней напрямую не общаются.

**Как получает задания (предложено).** Таблица заданий `BackgroundJob` в той же базе: вид, параметры (JSON),
файл (`bytea`, как сканы по ADR-0009), кто поставил, состояние (`Queued`, `Running`, `Done`, `Failed`), время,
итог или текст ошибки.
- Ставит задание только сервер — после проверки прав сотрудника (правило «права проверяет сервер»). Desktop отправляет
  файл, получает номер задания и спрашивает его состояние (`GET /api/jobs/{id}`); итог (загружено, расхождения)
  показывает, когда задание готово.
- Служба раз в несколько секунд забирает одно задание одним запросом:
  `UPDATE ... SET status = 'Running' WHERE id = (SELECT id ... WHERE status = 'Queued' ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING ...`.
  Ночные задания служба ставит себе сама по расписанию из настроек; уникальный индекс «вид + дата» не даёт поставить дважды.
- Минусы, честно: экземпляр службы один, и `SKIP LOCKED` здесь — страховка от случайно запущенного второго, а не нужда;
  это сырой SQL только для PostgreSQL (на SQLite не проверить — тесты только с `AVERS_TEST_POSTGRES`); опрос раз
  в несколько секунд даёт задержку старта (для реестров неважно; `LISTEN/NOTIFY` — если понадобится);
  задание, которое служба взяла и не закончила (падение, перезапуск), остаётся в `Running` — при старте служба
  переводит такие в `Failed` с текстом «прервано», повторяет сотрудник.
  Проще было бы условное `UPDATE ... WHERE status = 'Queued'` (как в `Payments.Record`) — тоже годится при одном экземпляре.

**Как не появляется двух писателей одной оплаты.**
- Служба пишет только через операции `Avers.Data` — те же, что вызывает обработчик сервера (внесение оплаты,
  отмена, загрузка файла). Своего SQL для денег в службе нет.
- Каждая оплата из реестра — по ADR-0010/0011: короткая транзакция с блокировкой строки абонента
  (`SELECT ... FOR UPDATE`), внутри проверка «месяц уже оплачен» и вставка `Payment`. Кассир и служба по одному абоненту
  выстраиваются в очередь на миллисекунды.
- Реестр пишется порциями (десятки–сотни строк на транзакцию), а не одной транзакцией на файл: иначе служба
  держала бы блокировки тысяч абонентов, и касса ждала бы.
- Повтор после обрыва не задваивает оплаты: у платежа из реестра есть ссылка на файл и номер строки
  с уникальным индексом (как номер строки `ABN_PAY` при переносе, ADR-0010).
- Схему базы меняет только сервер (миграции при запуске). Служба при старте проверяет, что неприменённых миграций нет,
  иначе не берёт задания и пишет в журнал «ждёт обновления базы».

**Журнал изменений.** Служба пишет в тот же `ChangeLog` в той же транзакции, что и правку. Кто — служебное имя
и сотрудник, поставивший задание: «Фоновая служба (задание № 123, поставил: Иванова (ivanova))»; у ночных — только
«Фоновая служба». Учётной записи для службы в таблице пользователей не заводим: войти под ней нельзя, отключать нечего.

**Развёртывание.** Проект `src/Avers.Worker` (`Microsoft.NET.Sdk.Worker`, `AddSystemd()` — журнал в journald).
В `deploy/server`: `avers-worker.service` (`Type=notify`, `User=avers`, тот же `EnvironmentFile=/etc/avers-server.env`,
`After=avers-server.service postgresql.service`, `Nice=10`, `Restart=always`). Сервер и служба — в одном архиве CI
`Avers-server-linux-x64`, `install.sh` ставит обе: останавливает службу, обновляет сервер (он применяет миграции),
ждёт `/health`, запускает службу. В строке подключения службы — небольшой пул (`Maximum Pool Size=5`):
по умолчанию Npgsql допускает до 100 соединений на процесс.

**Учебный режим Desktop.** Службы нет. `LocalStore` вызывает те же операции `Avers.Data` напрямую и ждёт результата,
как сейчас `OekImport.Apply`. Таблица заданий в учебной базе не используется.

## Последствия
- Касса не зависит от длины реестра и от сбоев обмена с 1С; службу можно перезапустить, не выкидывая сотрудников.
- Загрузка файла ОЭК переезжает в службу; экран загрузки в Desktop показывает состояние задания вместо мгновенного
  ответа. Меняется API загрузки — поднять `DesktopClient.Version` (ADR-0014).
- Логику загрузок пишем в `Avers.Data` (разбор файла — функция, тестируется на SQLite, как сейчас `OekImport`);
  в `Avers.Worker` — только цикл заданий, расписание и вызов этих функций.
- Работа службы видна администратору: `systemctl status avers-worker`, `journalctl -u avers-worker`; неудачное
  задание — `Failed` с текстом, его видит и сотрудник.
- Резервная копия (ADR-0013) службы не касается: всё состояние в базе.
- Ночные задания не ставить на время `pg_dump` (`deploy/server/avers-backup`).
- Не решено: какие ночные отчёты нужны и кому; форматы реестров — по исходникам ImportPay; включение OData в 1С
  ждёт ответов бухгалтерии (Q-05). Делать по мере этапов: сначала ОЭК (уже есть логика), потом реестры, потом 1С.
