# ADR-0010. Модель начислений и платежей

- Статус: Принято
- Дата: 2026-11-06
- Участники: Илья, архитектор

## Контекст
Сейчас на абонента и месяц — одна строка `YearPayment`: начисление (тариф) и оплата в одной записи
(уникальный индекс `SubscriberId, Year, Month` в `AversDbContext.cs`). Из этого следует:
- вторая оплата за месяц отклоняется («уже оплачен», `Payments.cs`) — нарушено REQ-ADS-04
  (видны все даты, если месяц оплачен несколькими платежами);
- в JACK `ABN_PAY` хранит один платёж в строке, при переносе второй и следующие платежи месяца теряются;
- отмена оплаты стирает сумму, дату и источник (`PaymentCancellation.cs`), след остаётся только в журнале;
- долг обрезается до нуля (`Billing.Debt`), переплата (аванс) не видна;
- отчёт «Для 1С» берёт источник и дату последнего платежа месяца, а не каждого платежа.

Не известно: считается ли месяц оплаченным при платеже 0 ₽ (Q-20) и что делать с оплатой ОЭК
за уже оплаченный месяц (Q-26); где в JACK признак физлицо/юрлицо/ТСЖ и отводы.

## Варианты
1. **Оставить строку на месяц, даты и суммы платежей — массивом в ней.** Минимум переделки. Минусы: источник,
   кассир и отмена нужны для каждого платежа — массив превращается в таблицу внутри строки; запросы
   «поступления по источникам за период» для 1С и сверки становятся разбором JSON, по-разному в PostgreSQL и SQLite;
   перенос `ABN_PAY` всё равно требует склейки.
2. **Начисление и платёж — разные таблицы, отмена — пометкой.** `Accrual` (абонент, месяц, сумма),
   `Payment` (много на месяц: сумма, дата, источник, кассир, плательщик, отметка об отмене).
   Плюсы: прямо ложится на `ABN_PAY`, любые отчёты — обычные `SUM ... GROUP BY`. Минус — переделка модели, экранов и тестов.
3. **То же, но отмена — сторно (отрицательная запись).** Бухгалтерски строго, записи не меняются никогда.
   Минусы: каждый запрос должен учитывать пары «платёж — сторно»; платёж 0 ₽ и его сторно по сумме неразличимы,
   а правило «месяц оплачен при любом платеже, в т.ч. 0 ₽» как раз на нуле и держится; неизменность записей
   уже обеспечивает журнал изменений.

## Решение
Вариант 2.
- `PaymentSource` — справочник источников (касса, банки, Почта, ОЭК…), переносится из `PAY_TYPE`.
- `Accrual` — одно начисление на абонента и месяц (уникальный индекс остаётся здесь).
- `Payment` — сколько угодно на месяц: абонент, оплаченный период (год, месяц), ссылка на `PaymentSource`,
  номер строки `ABN_PAY` для сверки переноса.
- Отмена — пометка (кто, когда, причина) плюс запись в журнале; отменённые платежи не входят в суммы, но видны в карточке.
- Сальдо знаковое: `Balance = Σ начислений − Σ неотменённых платежей`; `Debt = max(0, Balance)`, `Advance = max(0, −Balance)`. Деньги — `decimal`.
- Второй платёж за оплаченный месяц сервер принимает только с явным подтверждением в запросе; без него — отказ с текстом,
  Desktop показывает вопрос кассиру.
- Внесение и отмена — одна транзакция с блокировкой строки абонента: проверка «месяц уже оплачен» и вставка не разъезжаются
  при двух кассирах (общий подход — ADR-0011).
- До ответов сохраняются текущие правила: месяц оплачен при любом неотменённом платеже, в том числе 0 ₽ (Q-20);
  платёж ОЭК за оплаченный месяц — в расхождения (Q-26).
- Признак физлицо/юрлицо/ТСЖ и отводы — отдельными изменениями, когда станет ясно, где они в JACK.

## Последствия
- Отчёт для 1С и сверка ОЭК считают поступления по каждому платежу (его дата и источник).
- Карточка абонента показывает все платежи месяца, долг и аванс.
- Нужна миграция EF: `YearPayment` → `Accrual` + `Payment`, перенос имеющихся строк; `LastPaymentDate` пересчитывается из `Payment`.
- Старое рабочее место записало бы платёж по старой схеме — поднять `DesktopClient.Version` (правило 8 CLAUDE.md).
- План переноса (`docs/04-db-migration-plan.md`): `ABN_PAY` строка → `Payment`, сверка сумм с бухгалтерией (август 2026: ОЭК 4 914 739,57).
