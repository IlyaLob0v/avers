# 12. День переезда со старого Аверса на новый

Этот документ — план переключения: когда остановить старый Аверс, как перенести данные, сколько это займёт
и как вернуться назад, если что-то пойдёт не так. Технические подробности переноса — в
[04. План переноса базы](04-db-migration-plan.md) и [db/migration/README.md](../db/migration/README.md).

## Коротко

1. Заранее, без спешки, делаются **пробные переносы** на стенде, пока сверка не станет чистой.
2. В день переезда, после конца рабочего дня, старый Аверс **замораживается**: никто ничего не вводит.
3. Делается свежая выгрузка JACK, перенос на стенде и сверка. Если сверка сошлась — данные кладутся на сервер
   нового Аверса.
4. Утром сотрудники работают в новом Аверсе. Старый остаётся открытым **только на просмотр**.
5. Если сверка не сошлась или утром обнаружилась серьёзная ошибка — все продолжают работать в старом Аверсе,
   как будто ничего не было.

## До дня переезда

Переезд назначается, только когда выполнено всё из этого списка.

| Что | Кто | Как проверить |
|---|---|---|
| Сервер нового Аверса установлен, без учебных данных, ночные копии работают | администратор | [09. Сервер](09-server.md): `sudo avers-restore-check` заканчивается без ошибки |
| Заведены пользователи для всех сотрудников | администратор | каждый сотрудник один раз вошёл под своим именем |
| На всех рабочих местах новая версия программы | администратор | нигде нет сообщения «Обновите программу» |
| Стенд проходит самопроверку | разработчик | `bash db/stand/stand.sh selftest` → «САМОПРОВЕРКА ПРОЙДЕНА» |
| Пробный перенос настоящей выгрузки JACK сходится | разработчик | `bash db/stand/stand.sh all jack_full.dmp` заканчивается строкой «ИТОГ: перенос сошёлся» |
| Цифры бухгалтерии за месяц совпадают с новым Аверсом | бухгалтерия | итоги ОЭК и физлиц за проверочный месяц (август 2026) в отчёте нового Аверса и в бумажной сверке |
| 50 случайных абонентов проверены вручную | сотрудник АДС | карточка, оплаты и долг в старом и новом Аверсе одинаковые |
| Бухгалтерия ответила на вопросы про оплаты | бухгалтерия | [07. Открытые вопросы](07-open-questions.md): Q-19, Q-20, Q-26 (платежи частями, переплата, платёж в 0 рублей) и Q-32 (что из JACK не переносить) |
| Пробный перенос засечён по времени | разработчик | известно, сколько идёт каждый шаг (таблица ниже) |

Пробный перенос можно повторять сколько угодно: он работает только на стенде и ничего не меняет ни в старом,
ни в новом Аверсе.

## Когда переезжать

Лучше всего — **вечер пятницы**: на перенос остаются выходные, а если что-то пойдёт не так, в понедельник все
просто продолжают работать в старом Аверсе. Не стоит назначать переезд на последние дни месяца, когда вносятся
оплаты и готовятся отчёты для 1С и ОЭК.

Сотрудников предупредить за неделю: в пятницу после 17:00 старый Аверс закрывается на ввод, в понедельник
работаем в новом.

## Сколько это займёт

Точное время станет известно после пробного переноса настоящей выгрузки. Оценка по размеру базы (7 ГБ):

| Шаг | Примерно |
|---|---|
| Выгрузка JACK на сервере базы (`expdp`, [инструкция](11-jack-export.md)) | 1–2 часа |
| Копирование выгрузки на компьютер со стендом | до 1 часа |
| Восстановление в Oracle на стенде (`import`) | 1–2 часа |
| Расчёт начислений по месяцам (`accruals`) | несколько часов, самый долгий и неизвестный шаг |
| Перенос в PostgreSQL и сверка с Oracle (`schema`, `data`, `reconcile`) | 2–3 часа |
| Пробный перенос в таблицы Аверса и сверка (`transfer`) | до 1 часа |
| Перенос на сервер нового Аверса и сверка там | 1–2 часа |

Итого — от 8 до 15 часов. Поэтому команду `all` лучше запустить вечером в пятницу и оставить на ночь.

## Порядок в день переезда

**Пятница, 17:00 — заморозка.**

1. Предупредить всех, что ввод в старом Аверсе закончен. Убедиться, что никто не работает (все программы закрыты).
2. Записать на бумаге контрольные цифры из старого Аверса на этот день: число абонентов, сумма оплат за текущий
   месяц, общий долг. Их потом сравнивают с новым Аверсом.

**Пятница, вечер — выгрузка и перенос на стенде.**

3. Сделать выгрузку JACK по [инструкции](11-jack-export.md) и положить файл в `db/legacy/dumps/`.
4. На компьютере со стендом запустить весь перенос:

   ```bash
   bash db/stand/stand.sh all jack_full.dmp
   ```

   Команда останавливается на первой ошибке. В конце должно быть «ИТОГ: перенос сошёлся». Отчёт сверки —
   в `db/legacy/dumps/stand/legacy/transfer-check-…txt`. Строки «справка» прочитать глазами: это то, что
   по правилам не переносится (пустые абоненты для заявок на дом, проверки подключения, оплаты до 1998 года).

**Суббота — перенос на сервер нового Аверса.**

5. На сервере нового Аверса сделать копию базы до переноса — к ней можно вернуться:

   ```bash
   sudo avers-backup
   ```

6. На стенде выгрузить копию JACK из PostgreSQL одним файлом:

   ```bash
   docker compose -f db/docker-compose.yml exec -T postgres pg_dump -U avers -d avers -n legacy -Fc > db/legacy/dumps/legacy.dump
   ```

7. Перенести на сервер файл `legacy.dump` и папку `db/migration/transfer` (флешкой или по сети). Файл содержит
   персональные данные: после переноса удалить его с флешки.
8. На сервере остановить Аверс, загрузить копию JACK, перенести и сверить:

   ```bash
   sudo systemctl stop avers-server
   sudo -u postgres pg_restore --no-owner -d avers legacy.dump
   sudo -u postgres psql -d avers -v ON_ERROR_STOP=1 -f transfer/transfer.sql
   sudo -u postgres psql -d avers -v ON_ERROR_STOP=1 -f transfer/check.sql
   ```

   Последняя команда должна закончиться «ИТОГ: перенос сошёлся».
9. Убрать копию JACK из базы сервера (она остаётся на стенде и в самой выгрузке) и запустить Аверс:

   ```bash
   sudo -u postgres psql -d avers -c "drop schema legacy cascade"
   sudo systemctl start avers-server
   sudo avers-backup
   ```

**Суббота или воскресенье — проверка.**

10. Войти в новый Аверс и сравнить контрольные цифры из шага 2. Открыть несколько знакомых абонентов, домов
    и заявок.
11. Перевести старый Аверс в режим «только просмотр»: сотрудникам сказать, что вносить туда больше ничего нельзя.
    Сам сервер Oracle не выключать.

**Понедельник — работа в новом Аверсе.**

12. Весь день разработчик и администратор на связи. Ошибки записывать: что делали, у какого абонента, снимок экрана.

## Если что-то пошло не так

**Сверка не сошлась (шаг 4 или 8).** Переезд откладывается. Ничего возвращать не нужно: старый Аверс не менялся,
в понедельник все работают в нём, как обычно. Если сверка не сошлась на сервере, вернуть базу нового Аверса
к копии из шага 5 ([09. Сервер](09-server.md#восстановить-из-копии)) — там только пользователи и настройки.
Отчёт сверки передать разработчику.

**В понедельник найдена серьёзная ошибка** (неверные долги, не открываются карточки, не проходят оплаты).
До конца понедельника можно вернуться в старый Аверс:

1. Сотрудники закрывают новый Аверс и снова работают в старом.
2. Всё, что за понедельник внесли в новый Аверс (оплаты, заявки), переносится в старый вручную по журналу
   изменений нового Аверса. Поэтому окно возврата короткое: чем дольше работаем в новом, тем больше
   переносить руками.
3. Ошибку исправляют, и переезд повторяется в другую пятницу с самого начала.

**После понедельника** обратного пути в старый Аверс уже нет: ошибки исправляются в новом. Старая база Oracle
остаётся в режиме только для чтения как архив — минимум на год, чтобы при спорах с абонентами можно было
посмотреть старые данные.

## Что не переносится из JACK

Этого в старой базе нет, это заводится в новом Аверсе заново:

- судебные дела — из таблицы юристов «Дела Аверс», отдельной загрузкой после переезда;
- схемы домов, домофоны, паспорт дома (кабели, усилители, блоки питания, ключ от техэтажа);
- пользователи и права — их заводит администратор до переезда.

Оплаты до 1998 года (в неденоминированных рублях) не переносятся и остаются в архиве Oracle. Уволенные механики
не переносятся, но их фамилии сохраняются в старых заявках.
